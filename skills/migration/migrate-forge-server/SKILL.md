# Migrate a Forge server

A site lives on a Forge server whose PHP, MySQL or Ubuntu is too old. The move is **a new server next to the old one**, the site deployed there from an upgrade branch, tested on its `*.on-forge.com` name with a copy of the real data, then a short cutover: old site down, data copied once more, DNS switched, SSL issued, cron and daemons moved.

Everything on Forge goes through its API with `scripts/forge-api.sh`; sizes are searched and compared with `scripts/find-size.sh`; data moves with `scripts/transfer-data.sh`. The endpoints and payloads are in [reference/forge-api.md](./reference/forge-api.md); the DNS standard and the client email in [reference/dns.md](./reference/dns.md). Nothing here depends on Notion.

## How this skill behaves

Nine phases, **1/9 to 9/9**, in order, each ending at a checkpoint. The same words, the same layout and the same colours in every run, so the user recognises where they are without reading.

**Language.** Talk to the user in French. Plain sentences a non-developer could follow. Endpoints, payloads, ids and shell commands belong in the tool calls and in `state.json`, never in the prose: say « je crée le site sur le nouveau serveur », not `POST servers/1277711/sites {…}`. The only identifiers worth printing are server and site names, IPs, domains, sizes and branch names. The one exception is a command the user has to run themselves (then it goes in a fenced block, with the `!` prefix).

**Phase banner.** Every phase opens with this block, nothing above it in the message, then one sentence saying what the phase does and whether it writes anything:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  PHASE 3/9 · NOUVEAU SERVEUR
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

The nine titles, verbatim: `1/9 · INVENTAIRE`, `2/9 · BRANCHE DE MISE À NIVEAU`, `3/9 · NOUVEAU SERVEUR`, `4/9 · NOUVEAU SITE`, `5/9 · DOMAINES`, `6/9 · RÉPÉTITION DU TRANSFERT`, `7/9 · VRAI TRANSFERT (SITE HORS LIGNE)`, `8/9 · DNS ET SSL`, `9/9 · FINITION`.

**Checkpoint.** Every phase ends with the same four parts, in this order, and the message stops there:

1. `### Résultat` — one short table (what was checked or created, old vs new when it applies). Nothing that was not verified.
2. **One status line**, always one of these three, always first on its line:
   - `🟢 OK` — everything passed, nothing to read: the user can answer « go » without reading the table.
   - `🟡 ATTENTION` — something to know before going on (a default was changed, a step was skipped, a leftover to clean), explained in one or two sentences right after.
   - `🔴 DANGER` — the next phase takes the site down, changes DNS, deletes something, or a check failed. The sentence after it says exactly what is at stake and what the user must do or decide. The user's attention is required: never bury it in a list.
3. `### Prochaine phase N/9 · TITRE` — three to six sentences, in words, on what the next phase will do and what it writes where. No code, no endpoints. Decisions the user owns are asked here, as a list of fields with a default each (see phase 3 for the shape), never as a paragraph.
4. The last line is the question, alone: `Je lance la phase N/9 ?` (or the exact gate sentence a phase prescribes). Then stop and wait. **Never run two phases on one approval**, even when the user asks for both: do the first, checkpoint, ask again.

**Colours in the body.** `🔴` opens every line about downtime, DNS, deletions, production writes or secrets; `🟡` every warning worth reading; `🟢` every « tout est bon » at the end of a block. No other emoji.

**Writes.** Before a write, one line in words (« j'active le planificateur sur le nouveau site »). After it, the result in words (« planificateur actif, premier passage journalisé à 20:00 »). The numbered list of writes with their results is the `Résultat` table of the checkpoint.

**Waits.** A wait longer than two minutes (server provisioning, transfer, deployment, DNS) prints a one-line progress every two to three minutes (« transfert : base importée, copie du storage 2,1 Go sur 7 Go »). The user must never have to ask « où en est-on ? ».

**Inputs come from the repo and from Forge, not from the user**, except the decisions the user owns: server size, region, server name, on-forge name, database name, and the three gates (rehearsal → real transfer, DNS switch, archiving). Everything else is read, not asked.

**Permissions.** Phase 1 reads the production `.env`, the database size and Redis on the old server; the harness's auto mode refuses those reads unless the user allows them. The phase 1 banner says so in one `🟡` line and asks the user to allow the reads when prompted, before the first blocked call, instead of stopping three times.

**Secrets never reach the chat.** The token is read by the script, not printed. `.env` contents, database passwords and certificate keys are handled in files under `~/.forge-migrations/<project>/` (mode 600) and shown only as key names or masked values. Every secret of the new server lives in one file, `new-secrets.txt` (phase 3).

**The old server is read-only** until the real transfer. Until then the only write on it is deploying the upgrade branch (phase 6, with approval).

**State** is `~/.forge-migrations/<project>/state.json`, with these top-level keys and no others at the top level: `project`, `repo`, `production_branch`, `upgrade_branch`, `phase_reached` (integer 1–9, the last phase whose checkpoint was passed), `old` (server id, name, ip, provider, size, region, site id, root, db, domains, certificate, automation, other sites, redis), `target` (php, mysql, ubuntu, node), `decisions` (size, region, names, redis, zero-downtime, push-to-deploy, dns mode), `new` (server id, name, ip, site id, root, db, database id, domain ids, certificate ids, deployment ids), `transfers` (rehearsal and cutover timestamps and copies), `pending` (list of what remains for the user), `notes`. On start, if it exists, print `phase_reached` and the names, and ask whether to resume at the next phase or start over.

Blocking problem at any phase → stop, `🔴` line, what blocks and what the options are (lettered, with a recommended one first). Do not improvise around it.

## Phase 1/9 — Inventaire (read-only)

1. **Tooling.** `jq`, `curl`, `ssh`, `dig`, `gh` present; `scripts/forge-api.sh org` returns the organization slug (token in `$FORGE_API_TOKEN` or `~/laravel-forge-token`). No token → stop.
2. **Project.** From the cwd: `git remote get-url origin` → `owner/repo`. Slug = repo name (`luminaire-authentik-erp`). Production branch = `main` or `master` (whichever exists). Default database name = slug with `-` → `_` plus `_production`.
3. **Old site.** `GET sites?page[size]=100` (follow cursors), keep the sites whose `repository.url` ends with `owner/repo`. One match on the production branch → that is the old site; several → list them and ask which. **No match** (the site is a `Custom` repository deployed by Envoyer, or was created by hand): list the sites whose name contains the client's domain or the slug and ask which; record `old.deploy: envoyer` when `/home/forge/envoyer-lock` exists on the server, in which case the real `.env` is the shared one (`/home/forge/<project>/.env`, not Forge's, which is empty) and the deploy steps are Envoyer's hooks (ask the user for a screenshot or an export of them in this phase, not later). Record `old_server_id`, `old_site_id`.
4. **Old server.** `GET servers/{old}` → `name`, `ip_address`, `provider`, `size`, `region`, `ubuntu_version`, `php_version`, `database_type`. `GET servers/{old}/php/max-upload-size`, `php/max-execution-time`, `php/opcache`.
5. **Old site.** `GET sites/{old_site}` (org-scoped: `servers/{s}/sites/{site}` returns null attributes; the server-scoped path is for sub-resources only) → `name`, `root_directory`, `zero_downtime_deployments`, `shared_paths`, `deployment_retention`, `quick_deploy`, `repository.branch`, `database`, `https`. `GET .../deployments/script` → old script (keep it in state). `GET .../environment` → save to `~/.forge-migrations/<project>/old.env` (600). `GET .../domains` → each name, type, `www_redirect_type`, wildcard. `GET .../certificates`.
6. **Old automation.** `GET servers/{old}/sites`: every other site on the old server is listed in the inventory as **not migrated** (it blocks archiving; a non-Laravel site such as a Node process under pm2 moves with the recipe in [reference/forge-api.md](./reference/forge-api.md#non-laravel-site)). `GET servers/{old}/sites/{old_site}/scheduled-jobs`, `GET servers/{old}/background-processes` (keep those whose `directory` or `command` mentions the site path), `GET .../integrations/{horizon,laravel-scheduler,reverb,pulse,octane}`. A cron created by hand (`schedule:run` as a scheduled job, not the integration) is recorded as such: phase 7 deletes a job, not an integration.
7. **Old runtime over SSH** (`ssh forge@<old ip>`): `node -v`, `php -v`, `ls /etc/nginx/ssl/<domain>/`, `du -sh <site>/storage`, `mysql` database size (`SELECT table_schema, ROUND(SUM(data_length+index_length)/1024/1024) FROM information_schema.tables GROUP BY table_schema`), Laravel version (`composer.lock`). Sizes decide whether the transfer through the Mac is fine (it is, up to a few GB) and inform the server size.
   **Redis is data until proven otherwise**: `redis-cli -a <REDIS_PASSWORD> info keyspace` and a `--scan` sample grouped by pattern (digits → `N`). Keys without TTL that are not `laravel_cache`/sessions are application state (price histories, game state) that the app reads back: record `redis: data` in state and plan the Redis transfer in phases 6 and 7 (recipe in [reference/forge-api.md](./reference/forge-api.md#redis-transfer)). Only session and cache keys → `redis: cache`, nothing to move. When the read is refused and the user says the data does not matter, record `redis: skipped (user)`.
8. **DNS.** For every domain in step 5, and for `www.<domain>` when `www_redirect_type` is not `none`: `dig +short <name>`. A `www` with no record is recorded as `www: no-dns` (phase 8 drops the redirect before Let's Encrypt, which otherwise fails on `www`). Classify, and record it as `decisions.dns`: `witify` (CNAME to `<x>.prod.hosting.witify.io`: the switch is ours, one record in Cloudflare), `client` (A record to the old IP: the client must change it, see [reference/dns.md](./reference/dns.md); flag it now, `🟡`, because it decides the shape of phase 8), or `proxy` (the client cannot change it in time: the old server will relay the traffic, phase 8 variant).
9. **Target versions.** PHP `php83` (the lowest 8.x that new Forge servers offer; never higher unless the project already requires it), MySQL `mysql84`, Ubuntu `26.04`, Node = the server's (22 on fresh Ubuntu 26.04 servers; phase 2 makes the build pass on it).

Print the inventory as one table (old vs target) and the list of things that will have to move (jobs, daemons, integrations, domains, www behaviour, certificates). Write `state.json`. **Checkpoint.** The next-phase text names the DNS mode in one sentence, so the user knows from the start who will change DNS and when (phase 8, on request, never before).

## Phase 2/9 — Branche de mise à niveau, with deep verification

Branch `chore/forge-migration` from the production branch (reuse it if it exists). The goal is a branch that runs on PHP 8.3, MySQL 8.4 and the target Node, with the test suite green. No framework upgrade unless PHP 8.3 forces it.

1. `composer.json`: `"php": "^8.3"`; `composer update --with-all-dependencies` resolved on PHP 8.3 (Herd: `php8.3` binary, else `composer update --ignore-platform-req=php` is **not** acceptable: find a PHP 8.3). First run `composer why-not php 8.3` with the PHP 8.3 binary: when it reports nothing, the lock already runs on 8.3 and only the constraint changes (`composer update --lock`), no package moves. Abandoned or incompatible packages replaced, not pinned. Leftovers from another host (Vapor config, `vapor.yml`, `public/vendor/vapor-ui`; Envoyer heartbeats in `Kernel.php`) removed. A framework past end of life (Laravel 9) whose packages carry security advisories: Composer 2.10+ refuses them and silently falls back to a `dev` branch; `config.audit.ignore` with the advisory ids plus `minimum-stability: stable` keeps the release, and the framework upgrade itself is a separate project, offered as option B, never done here.
2. PHP 8.3 breakages: run the suite and `vendor/bin/phpstan` if present; grep for `utf8_encode|utf8_decode|\$\{[a-z_]+\}|each\(|create_function|FILTER_SANITIZE_STRING`, dynamic properties on plain classes, `strftime`. Fix what is found. **Timezone aliases:** Ubuntu 26.04 ships without `tzdata-legacy`, so `config('app.timezone')` (and any `Carbon`/`DateTimeZone` literal) set to an old alias (`Canada/Eastern`, `US/Eastern`, `EST5EDT`…) makes every artisan command die with `Timezone ID '…' is invalid`. Replace it with the canonical name (`America/Toronto`, `America/New_York`): same rules, same stored times.
3. **MySQL 8.4.** Every foreign key must reference a unique or primary column, otherwise `ERROR 6125 Missing unique key for constraint` on migrate and on import. Fix with a migration that adds the `unique` index and update `database/schema/mysql-schema.dump` when it exists. **This fix must be deployed on the old server before the data export** (the export carries the schema): record it in `pending` for phase 6. `mysqldump` needs `--no-tablespaces` (the transfer script has it).
4. Node: the assets are built on the new server, so the build must pass on **the server's Node** (22 on fresh Ubuntu 26.04 servers), whatever `.nvmrc` says; set `.nvmrc` to it. Test it with `npx -y -p node@22 -- sh -c 'npm ci && npm run production'` (or `build` for Vite). `node-sass` → `sass` when it fails to build. Mix 6 projects fail on Node 17+ with `ERR_OSSL_EVP_UNSUPPORTED` (md4 hash): bump only the culprits, `npm install -D webpack@~5.75.0` (webpack ≥ 5.61 has its own md4; **5.107+ breaks laravel-mix 6**, `Cannot find module 'webpack/lib/SizeFormatHelpers'`, hence the `~`) and `npm update babel-loader` (≥ 8.2.4). Never `npm update laravel-mix`: it cascades through hundreds of packages and breaks the ProgressPlugin options. `npm ls 2>&1 | grep -c invalid` must be 0, and the build must still pass on the old Node.
5. CI on the branch runs PHP 8.3 with a `mysql:8.4` service and the target Node (`.github/workflows/*.yml`); `migrate:fresh` plus the suite must pass there. Read the workflow's `on:` block first: when it only fires on the production branch or on pull requests, open a **draft PR** (`gh pr create --draft`) to get a run; it is merged in phase 9. Push, `gh run watch`, read the result.
6. Commit the upgrade on the branch. Do not merge.

Report the verification as a checklist with pass/fail per item. A fail that cannot be fixed on this branch (framework too old for PHP 8.3, a package with no PHP 8.3 release, a schema change the business must validate) is **blocking**: stop, `🔴`, lettered options. Green → **Checkpoint.** The next-phase text carries the server questions of phase 3, so the user answers them once and phase 3 starts on « go ».

## Phase 3/9 — Nouveau serveur

1. Provider and credential: the old server's `provider` (`laravel` → Laravel VPS, `ocean2` → DigitalOcean); `GET /orgs/{org}/server-credentials` → the credential whose `provider` matches. Regions: `GET /providers/{p}/regions`; the default is **Toronto** (`tor1`) whatever the old server's region, and the old region is shown beside it when it differs.
2. Sizes: `scripts/find-size.sh --like {old_server_id}` prints the old server's live capacity (vCPU, RAM, disk used, load average, CPU model) and the sizes with the same RAM and vCPU on **both** DigitalOcean and Laravel VPS (id, code, RAM, vCPU, disk, USD per month, name). Print that table with the storage/database sizes from phase 1 beside it, and say which rows are the same family as the old server (premium Intel, premium AMD, dedicated, standard). When the user describes what they want in words (`premium intel 8gb 4vcpu laravel`), run `scripts/find-size.sh <those words>` and print the result; repeat until a row is chosen. Prices are not in the Forge API; the script reads them from two public pages (DigitalOcean's pricing page by slug, Laravel VPS's price JSON, Business tier) and marks `?` when a size has none. They are indicative: the Forge size picker is the reference. There is no resize in the API: a size changed later is done by the user in Forge's UI, then `nproc` and the services are re-checked.
3. **Ask the user**, one message, five fields, each with its default, in exactly this shape (the user answers field by field, or « ok » for all the defaults):

   ```
   Taille      : <provider + size code + family>, <RAM>/<vCPU>/<disk>, <price>   (ligne du tableau)
   Région      : Toronto (tor1)
   Nom serveur : <old server name without a trailing -N>
   Nom on-forge: <slug>   → <slug>.on-forge.com
   Base        : <slug_with_underscores>_production
   ```

   The size has no default when the table offers several families: the recommended row is named, the user picks. The skill never chooses the size.
4. Announce and send `POST servers` with `type: app`, `ubuntu_version: 26.04`, `php_version: php83`, `database_type: mysql84`, `<provider>: {region_id, size_id, …}` with the **codes** on both providers (DigitalOcean `tor1`, `s-1vcpu-1gb`; Laravel VPS `tor1`, `7`: the numeric ids answer `404 No query results for model [ProviderRegion]` or `[ProviderSize]`), and for DigitalOcean the mandatory `vpc_uuid` (see the cheat sheet). A `429` is Forge's rate limit: wait 75 s, check that no server was created, send again. The `202` response carries `meta.sudo_password` and `meta.database_password`: write them to `~/.forge-migrations/<project>/new-secrets.txt` (600) **before** saving or printing anything else from the response. That single file holds every secret of the new server, one per line, in this exact format (the IP line is filled in step 5, the DB reader line in step 8):

   ```txt
   IP : <new ip>
   Sudo : <sudo password>
   DB : <forge database password>
   DB reader : <reader password>
   ```

   Read a value with `sed -n 's/^DB : //p' new-secrets.txt` (`Sudo`, `DB reader`); never print the file. Record `new.server_id`. `forge-api.sh wait servers/{new} '.data.attributes.is_ready' true 1200 30`, with a progress line every few minutes.
5. Once ready: `GET servers/{new}` → `ip_address` (fill the `IP` line of `new-secrets.txt`); `ssh forge@<new ip> 'node -v; php -v; mysql --version'`. The organization's SSH keys land a few seconds **after** `is_ready`: on `Permission denied`, wait 30 s and retry twice before adding a key (`POST servers/{new}/ssh-keys` with the user's public key creates a duplicate otherwise). Node lower than the target → stop and say so (a Forge recipe or `n`/`nvm` on the server is a decision for the user).
6. PHP settings, same as the old server, **three separate calls** (the upload endpoint ignores the other two fields): `PUT servers/{new}/php/max-upload-size {max_upload_size}`, `PUT .../php/max-execution-time {max_execution_time}`, and `POST .../php/opcache` unless `GET .../php/opcache` already says `opcache_enabled: true`. Verify with GET and print old vs new.
7. Database: keep the `forge` password Forge generated in step 4 (`DB` in `new-secrets.txt`); `POST servers/{new}/database/schemas {name: <db name>}`; wait `status == installed`. Record `new.database_id`.
8. **Read-only database user**, created now so the user stores every secret at once: a random 32-character password (`openssl rand -base64 33 | tr -d '/+=\n' | cut -c1-32`) written to the `DB reader` line of `new-secrets.txt`, `POST servers/{new}/database/users {name: reader, password, database_ids: <every schema id from GET .../database/schemas>, read_only: true}`, wait `installed`. Forge ignores `read_only` and grants `ALL PRIVILEGES … WITH GRANT OPTION`: as `forge`, run `REVOKE ALL PRIVILEGES, GRANT OPTION FROM reader@'%'` then `GRANT SELECT, SHOW VIEW ON <db>.* TO reader@'%'` for each schema, then check `SHOW GRANTS FOR reader@'%'` lists only `SELECT, SHOW VIEW`. The write test is `CREATE TABLE zz_reader_test (id int)` as `reader` **on the empty new database only, never on the old server**: it must be denied; if it succeeds the grants are wrong, drop the table and redo the revoke. A later edit of this user in Forge may restore the full grants.

**Checkpoint** with server name, IP, versions, PHP settings and database name, plus the path of `new-secrets.txt` (never its values), as a `🔴` line: the user copies the IP, sudo, `forge` database and `reader` database entries into the password manager now, in one go. They are verified in phase 9.

## Phase 4/9 — Nouveau site, .env, script de déploiement

1. **Site.** `POST servers/{new}/sites` with `type: laravel`, `domain_mode: on-forge`, `name: <on-forge name>`, `php_version: php83`, **`zero_downtime_deployments: true` always**, `shared_paths: [{from: storage, to: storage}]`, `source_control_provider: github`, `repository: owner/repo`, `branch: chore/forge-migration`, `database_id`, **`push_to_deploy: true`** (a push on the upgrade branch redeploys the test site, which is what the rehearsal wants). When the old site had no zero-downtime (plain `git pull` in its directory, or Envoyer), say so in one `🟡` line at the checkpoint of phase 3 (« l'ancien site déployait sans zero-downtime; le nouveau l'aura, le script de déploiement est réécrit en conséquence ») and go on: it is not a question. Wait `status == installed`, then `repository.status == installed` (poll `GET sites/{new_site}`, org-scoped). Then `GET sites/{new_site}` → `web_directory`: Forge creates on-forge sites with the web directory at the site root, which serves a 403; `PUT servers/{new}/sites/{new_site} {directory: "/public"}` (server-scoped; the org-scoped path answers 405) and check `web_directory` ends with `/public`. If the old site had `deployment_retention`, same `PUT` with `{deployment_retention}`. Record `new.site_id`, `new.site_name`, `new.root` (`/home/forge/<name>.on-forge.com`), knowing that **phase 5 renames it**.
2. **.env.** Build `new.env` from `old.env` (or from the Envoyer shared `.env` of phase 1 step 3):
   - every line containing an old domain name (from phase 1) → the on-forge name (`APP_URL`, `SESSION_DOMAIN`, `SANCTUM_STATEFUL_DOMAINS`, `ASSET_URL`, `REVERB_HOST`, `VITE_*`…);
   - `DB_DATABASE` → new name, `DB_PASSWORD` → new password, `DB_HOST` stays `127.0.0.1`; `DB_USERNAME` stays `forge`;
   - `REDIS_PASSWORD`: the new server has no Redis password by default → keep the line only if `ssh forge@<new> 'redis-cli ping'` answers `NOAUTH`; otherwise set it empty and say so;
   - everything else unchanged (mail, S3, Pusher, keys);
   - older projects only: when the app uses Sanctum's SPA auth and `config/sanctum.php` hard-codes the production domains as the `SANCTUM_STATEFUL_DOMAINS` default (the `.env` has no such key), add `SANCTUM_STATEFUL_DOMAINS=<old domains>,<name>.on-forge.com`; otherwise every API call from the on-forge name answers `Unauthenticated.` It can stay as is after the cutover.
   Print the diff as **key names plus the new value for domain/database keys, masked for anything else**. `PUT sites/{new_site}/environment {environment, cache: true, queues: true}` is **async**: before deploying, `GET .../environment` until `APP_URL` and `DB_DATABASE` read back with the new values (a deployment started too early runs with the old `.env` and fails on the first thing that needs the network or the database).
3. **Deploy script.** `GET sites/{new_site}/deployments/script` is the one Forge just wrote. Rewrite it so that it keeps Forge's zero-downtime skeleton (`$CREATE_RELEASE()`, `$FORGE_COMPOSER`, `$FORGE_PHP`, `$ACTIVATE_RELEASE()`, `$RESTART_QUEUES()`) and carries over, in the same order, every custom step of the old script or of the Envoyer hooks: artisan commands specific to the project (`artisan production`, `storage:link`, `optimize`, `horizon:terminate`…), the asset build the old script used (`npm ci && npm run production` for Mix, `npm run build` for Vite), anything else. Hard-coded `php8.x` becomes `$FORGE_PHP`. Keep `artisan optimize` when the old script had it. Print old and proposed scripts side by side (this is the one place a script is shown in full). `PUT .../deployments/script {content, auto_source: <old value>}`.
4. **Deploy.** `POST sites/{new_site}/deployments` → id; a `null` answer is a transient 404 on a write (never mask the HTTP status): list the deployments, and only send again when none started. `forge-api.sh wait sites/{new_site}/deployments/{id} '.data.attributes.status' finished 900 15`. On `failed`: `GET .../deployments/{id}/log`, print the failing lines, fix (script or branch), redeploy. Loop until finished. A deployment that finishes in seconds is read in the log too.
5. **Smoke.** `*.on-forge.com` sits behind Cloudflare, which answers 403 to curl's default agent: `curl -s -o /dev/null -w '%{http_code} %{redirect_url}' -A "Mozilla/5.0" https://<name>.on-forge.com/` → 200 or a redirect to login (the on-forge name has its own certificate); a 403 with `server: nginx` in the body is the web directory of step 1. Then, over SSH in `current/`, `php artisan env` and a `tinker --execute` printing `config('app.url')`, the database name, cache/session/queue/broadcast drivers, `PHP_VERSION` and `app()->version()` (`artisan about` only exists from Laravel 9). MySQL may still be restarting right after the first deployment: a `connection refused` here is retried once after 20 s.

Horizon, scheduler, Reverb and Pulse stay **off** on the new site until the cutover. **Checkpoint.**

## Phase 5/9 — Domaines on the new site (no SSL yet)

For every domain of the old site, in the old order, `POST sites/{new_site}/domains {name, allow_wildcard_subdomains: <old>, www_redirect_type: <old value>}` — the old `www_redirect_type` is the answer to "was www active": `from-www`/`to-www` are kept as they were, `none` stays `none`. Wait `status == enabled`. Then `POST domains/{d}/actions {action: mark-as-primary}` on the domain that was primary on the old site. **Marking a domain primary renames the site directory** to `/home/forge/<domain>` (`current`, `storage`, `.env` move with it; nginx is rewritten): re-read `GET sites/{new_site}` → `root_directory` and update `new.root` in state (the transfer script's `--dst-dir` comes from there). The on-forge name keeps its own nginx server block and keeps serving the tests, even though `GET .../domains` may no longer list it. The rename leaves the cached config and `current/public/storage` pointing into the old `/home/forge/<name>.on-forge.com/...` path, and the site answers 500 within a couple of minutes (OPcache has `validate_timestamps` off): **redeploy right away** (phase 4 step 4), which rebuilds the config cache and the `storage:link`; then delete the stray `/home/forge/<name>.on-forge.com` directory the app may have recreated, and check the on-forge name answers 200/302 again. A site using Laravel's `TrustHosts` answers 404 on the custom domain until `APP_URL` carries it (phase 8): expected, not a fault. No certificate is requested here. Print `GET .../domains` for both sites side by side. **Checkpoint.** The next-phase text warns, `🟡`, that the rehearsal site runs with the production mail, payment and integration keys, and offers once to set `MAIL_MAILER=log` and the integration flags off for the rehearsal.

## Phase 6/9 — Répétition du transfert (old site stays online)

Before this phase, the MySQL 8.4 fix from phase 2 step 3, if any, must be live on the old server: deploy the upgrade branch there only with explicit approval (`PUT sites/{old_site}/git {branch: chore/forge-migration}` + deployment, and record that the old site now runs the upgrade branch), or cherry-pick the migration onto the production branch and deploy that.

Run, with every value filled from state:

```bash
scripts/transfer-data.sh --mode test \
  --src forge@<old ip> --src-dir <old root_directory without /current> --src-db <old DB_DATABASE> \
  --dst forge@<new ip> --dst-dir <new.root> --dst-db <new db name> --dst-php php8.3
```

It exports the database (`--single-transaction --quick --routines --triggers --no-tablespaces`), backs up the destination database first, imports, copies `storage/` without logs and caches, then runs `storage:link`, `migrate --force`, `optimize:clear`, `queue:restart`, `up` with PHP 8.3. Passwords are read from each server's `.env` over SSH. Copies stay in `~/Downloads`. After it, **redeploy** (phase 4 step 4): the `optimize:clear` dropped the config cache and the copied `storage/` may carry a stale `down` file.

With `redis: data` in state, follow it with the Redis transfer ([reference/forge-api.md](./reference/forge-api.md#redis-transfer)).

**Verify with exact counts**, never `information_schema.table_rows` (an estimate that reads 0 on freshly imported tables): the same `SELECT COUNT(*)` on the three or four biggest tables plus `MAX(updated_at)` of the main one, on both servers, `find storage/app -type f | wc -l` on both, and `redis-cli dbsize` plus three sampled keys read on both when Redis moved. Print the table old vs new; a difference not explained by rows created on the old site after the dump (`created_at` later than the dump time) is blocking.

Then the user tests on `https://<name>.on-forge.com`: login, a few records, images from `storage`, a PDF or export, a queued job (`POST .../commands {command: "php artisan queue:work --once"}`), and `php artisan schedule:list`. Problems → fix on the branch, redeploy (phase 4 step 4), transfer again if the data is involved. **Checkpoint**, with this `🔴` block in the next-phase text, verbatim, because the next two phases are the downtime:

> 🔴 La phase 7 met l'ancien site en maintenance et il le reste jusqu'au changement de DNS (phase 8). Les deux phases s'enchaînent sans pause : prévois 15 à 30 minutes, de préférence hors des heures d'activité. **Ne change pas le DNS avant que je te le demande**, à la phase 8, une fois le certificat et le `.env` de production en place sur le nouveau serveur.

The gate is the user's clear validation of the rehearsal, in their own words (« tout bon », « répétition validée », « go pour 7 » all count).

## Phase 7/9 — Vrai transfert (site hors ligne)

Only after the user validated the rehearsal. Open with the banner, then ask once more, alone on its line, in these words: **« 🔴 Vrai transfert : l'ancien site sera mis hors ligne maintenant. Confirmer ? »** Proceed only on a clear yes.

1. **Stop automation on the old server first, before the export** (announce, then run), so no scheduled import, token refresh or queued job writes to the old database after the export, and the two schedulers never run at once (a rotating OAuth refresh token used on both sides invalidates one of them): `DELETE servers/{old}/sites/{old_site}/integrations/laravel-scheduler` when it was enabled, else `DELETE` each site scheduled job by id (the server-wide `scheduled-jobs` list holds them); `POST servers/{old}/background-processes/{p}/actions {action: stop}` for each daemon of the site; `DELETE .../integrations/horizon`, `/reverb`, `/pulse` for each one that was enabled. Old daemons are stopped, not deleted, so the inventory stays visible on the old server. Then wait until `ssh forge@<old> 'ps -u forge -o cmd | grep -c "[a]rtisan"'` reads 0. Before the cutover, read `app/Console/Kernel.php` and tell the user how polled integrations catch up (an import that re-reads the last N hours loses nothing as long as the downtime stays under N).
2. **Production `.env` on the new site, now**: every key phase 4 rewrote to the on-forge name goes back to the production domain (`APP_URL`, `SESSION_DOMAIN`, `SANCTUM_STATEFUL_DOMAINS`…); with `decisions.dns: proxy`, add `TRUSTED_PROXIES=<old ip>` (the app's `TrustProxies` must read it; check the middleware). `PUT .../environment {environment, cache: true, queues: true}` and read `APP_URL` back. From here the on-forge name may answer 404 (`TrustHosts`): the checks below use `curl --resolve <domain>:443:<new ip>`.
3. `scripts/transfer-data.sh --mode cutover ...` (same flags). The old site goes `artisan down` before the export and stays down. A rollback is `ssh forge@<old> "cd <old code dir> && php artisan up"` plus restarting what step 1 stopped; the script prints the first part. Progress lines every two to three minutes.
4. Redis transfer again when `redis: data` (the dump is taken after `artisan down`, so it carries the last writes). Then the same exact-count table as phase 6, plus a check that the latest data is there (a record created on the old site just before the cutover). Redeploy (the script's `optimize:clear` dropped the config cache). When Redis was not transferred, `redis-cli dbsize` on the new server must be 0 or hold only cache keys: a job queued while the user tested the rehearsal would run against production data as soon as Horizon starts; clear those queues first.
5. **Start automation on the new site**, mirroring the inventory: `POST sites/{new_site}/integrations/laravel-scheduler`; `POST .../integrations/horizon` when Horizon was enabled; `POST .../integrations/reverb {host: ws.<domain>, port, connections}` with the old values; `POST .../integrations/pulse` when enabled; each other daemon recreated with `POST servers/{new}/background-processes` (command with `php8.x` → `php8.3`, `directory` with the old root → the new root, same `processes`, `site_id: new_site`). Wait `status == running` on each. Every site scheduled job that was not the Laravel scheduler is recreated with `POST sites/{new_site}/scheduled-jobs` with the same `cron` and the path rewritten.
6. Print `GET` of jobs, daemons and integrations on both servers side by side. **Checkpoint**, short: the site is still down, phase 8 starts on « go » and ends the downtime. `🔴` reminder: still no DNS change.

**If the user changed DNS early** (a screenshot arrives mid-transfer): do not argue, protect the visitors. Immediately install the copied certificate (phase 8 step 1), put the **new** site in maintenance (`artisan down` in `new.root/current`) so nobody sees rehearsal data being overwritten, finish the transfer, redeploy, `artisan up` on the new site, then continue at phase 8 step 2 and skip step 3.

## Phase 8/9 — DNS et SSL

1. **Certificate without a gap.** Copy the old certificate: `ssh forge@<old> 'cat /etc/nginx/ssl/<domain>/<id>/server.crt'` and `server.key` (Forge leaves them world-readable; `sudo` on the old server asks for a password the skill does not have) into `~/.forge-migrations/<project>/` (600), then `POST sites/{new_site}/domains/{primary}/certificates {type: existing, enable: true, existing: {key, certificate}}`; wait `status == installed`, and `openssl s_client -connect <new ip>:443 -servername <domain>` must show it. Record `new.existing_certificate_id`. Skip when the old site had no certificate. When the old certificate also covered alias domains, the aliases get their own Let's Encrypt certificate in step 4 right after the primary's; until then they fail the TLS handshake, so say it, `🟡`, with the expected duration (a few minutes).
2. Check the new site answers on the production domain before anyone is sent to it: `curl -s -o /dev/null -w '%{http_code}' --resolve <domain>:443:<new ip> https://<domain>/` → 200/302.
3. **DNS switch. This is the moment, and the only one, where the user changes DNS.** Print it as a `🔴` block, with nothing else in the message, then wait:
   - `decisions.dns: witify` → « 🔴 **Change le DNS maintenant** : Cloudflare → zone `witify.io` → enregistrement A `<slug>.prod.hosting` → IPv4 `<old ip>` devient `<new ip>`, mode DNS only. Écris-moi « dns changé » quand c'est fait. » Then loop `dig @1.1.1.1 +short <domain>` every 30 s until it ends with the new IP (timeout 30 min, then ask), with a progress line every two minutes.
   - `decisions.dns: client` → the client makes the change: draft the email from [reference/dns.md](./reference/dns.md), never send it; the old site stays in maintenance until the client's record points to the new IP, and the user decides whether to wait or to switch to the `proxy` variant below.
   - `decisions.dns: proxy` (the client cannot change DNS in time): the old server forwards the traffic instead, and step 4 waits until the client's CNAMEs exist:
     - Still point the Witify name at the new IP (the user does it in Cloudflare, same `🔴` block), so the client email stays valid.
     - Save the old site's nginx config (`GET servers/{old}/sites/{old_site}/nginx` → `content`) to `old-nginx.conf` (600), then write `proxy-nginx.conf`: same file, with `location /`, the favicon/robots locations, `error_page` and the PHP `location` replaced by a `location /` that does `proxy_pass https://<new ip>`, `proxy_ssl_server_name on`, `proxy_ssl_name <domain>`, `proxy_http_version 1.1`, `Host $host`, `X-Real-IP`, `X-Forwarded-For`, `-Proto`, `-Host`, `-Port`, `proxy_read_timeout` above the PHP max execution time, `proxy_buffering off`, plus `client_max_body_size` equal to the upload limit. Keep the certificate lines, the `forge-conf` includes (the Let's Encrypt challenge location lives there, so the old certificate keeps renewing) and the `access_log`/`error_log` lines. Show the diff.
     - The new site needs the copied certificate (step 1) before the switch: the proxy connects to it over HTTPS with SNI `<domain>`.
     - `PUT servers/{old}/sites/{old_site}/nginx {config: <proxy-nginx.conf>}` (the field is `config`; `content` answers 422). Then check: `grep proxy_pass` in `/etc/nginx/sites-available/<domain>` on the old server, `https://<domain>/` answers like the new site, a `storage` file answers 200, a file written to `/home/forge/.letsencrypt/` on the old server is served at `/.well-known/acme-challenge/<file>` (delete it after), and the visitor's real IP reaches the app (hit a throttled route, then `redis-cli -n 1 exists <cache prefix>:<md5(limiter name . key)>` with the Mac's public IP must be 1 and with the old IP 0; the cache is Redis database 1).
     - Rollback is `PUT .../nginx {config: <old-nginx.conf>}`, `artisan up` on the old site and the old cron recreated. **Never empty the old server** (`.env`, `releases/`, databases) while it relays: the rollback needs them, and the relay needs nginx.
     - Phase 9 leaves the old server running (it serves the traffic), and the final report lists what remains: client CNAMEs, then Let's Encrypt on the new site, then archiving the old server.
4. **Let's Encrypt.** Forge adds `www.<domain>` to the request whenever `www_redirect_type` is not `none`, and HTTP-01 fails on a name without DNS. With `www: no-dns` from phase 1, first `PATCH .../domains/{primary} {www_redirect_type: none}` (or the user adds the `www` record and the redirect is kept). Then `POST .../domains/{primary}/certificates {type: letsencrypt, letsencrypt: {verification_method: http-01, key_type: ecdsa}}`; wait `status == installed && active == true`. A `404` on this `POST` is transient: list the certificates, send again only when none was created. On `failed`, the reason is in `/root/.letsencrypt-renew/<cert id>.out` on the new server (sudo with the `Sudo` line of `new-secrets.txt`); `DELETE` the failed certificate before retrying so Forge's list stays clean. Check the served certificate with `openssl s_client -connect <new ip>:443 -servername <domain> </dev/null | openssl x509 -noout -text | grep -A1 'Subject Alternative Name'` (`-ext` is not available on macOS's openssl): `www.` must be there when the redirect was kept. **Certificates are per domain:** the primary's certificate covers only `<domain>` and `www.<domain>`, never the aliases (the old Forge put every alias in one certificate). Request the same Let's Encrypt certificate on **each alias domain** right after the primary's, and check each name with `openssl s_client -servername <alias>` and a `curl --resolve`; an alias without its certificate fails the TLS handshake (`curl` code `000`). With Reverb: domain `ws.<domain>` plus its own certificate the same way.
5. **Remove the copied certificate.** Once the Let's Encrypt certificate is `active` and served (step 4 check), `DELETE sites/{new_site}/domains/{primary}/certificates/{new.existing_certificate_id}` and `GET .../certificates` must list only the Let's Encrypt ones. An inactive copy left in Forge expires in weeks and confuses the next person. Then delete the local `server.crt`/`server.key`.
6. `curl -s -o /dev/null -w '%{http_code}' --resolve <domain>:443:<new ip> https://<domain>/` → 200/302. The Mac's own resolver caches the old answer for a while: judge the switch with `dig @1.1.1.1`, never with a plain `curl` or Chrome. **Checkpoint**: `🟢 Le site est en ligne sur le nouveau serveur` when everything passed; the downtime is over here.

## Phase 9/9 — Finition

1. Merge `chore/forge-migration` into the production branch (PR through `gh pr create`; the user merges, or asks for it to be merged, and may ask for `dev` to be updated too). After the merge: `PUT sites/{new_site}/git {source_control_provider: github, repository, branch: <production branch>}`, deploy, wait `finished`, and check the deployment's commit is the merge commit.
2. **Push to deploy, verified:** `GET sites/{new_site}` must read `quick_deploy: true` (set at creation in phase 4); if not, `POST sites/{new_site}/deployments/push-to-deploy` and read it back. When the old site was deployed by Envoyer (`/home/forge/envoyer-lock` on the old server, a `Custom` repository in Forge), tell the user to disable the project in Envoyer: its next deployment would otherwise land on the old server.
3. **Secrets check with the user**, once all four lines of `new-secrets.txt` are in the password manager (phase 3 checkpoint):
   - TablePlus, from the password manager entries only: a MySQL connection over SSH, SSH `forge@<new ip>` with the user's key, MySQL `127.0.0.1:3306`, user `forge` then user `reader`, database `<db name>`. Both must connect; `reader` must list the tables and refuse an edit.
   - Sudo: the user runs `ssh -t forge@<new ip> 'sudo -k; sudo -v && echo sudo-ok'` and pastes the password from the password manager; `sudo-ok` must print.
   - A failure means the entry was copied wrong: compare it with `new-secrets.txt` without printing either.
4. The on-forge name stays as an alias (harmless) unless the user wants it removed (`DELETE .../domains/{d}`).
5. Old server: the site stays in maintenance, its automation stopped. Say that it can be archived after a few quiet days (`POST servers/archives` is a decision for the user, never done here), and only once every other site of the old server (phase 1 step 6) has moved. Delete `~/.forge-migrations/<project>/old.env`, `new.env`, the certificate files, the raw server-creation response and, unless `decisions.dns: proxy`, the nginx copies; delete `new-secrets.txt` only after step 3 passed; keep `state.json`.
6. Final report, then `🟢`: old and new server names and IPs, domains with certificate status, what runs where (jobs, daemons, integrations), the rollback in three sentences, and the `pending` list from state: `~/Downloads` copies to delete once the migration is a week old, the old server to archive, anything the client still has to do.

## Rollback at any point before phase 8

The old site is untouched (phase 6) or in maintenance (phase 7): `php artisan up` on the old code directory brings it back, and the stopped daemons restart with `POST .../background-processes/{p}/actions {action: start}`, the scheduler with `POST .../integrations/laravel-scheduler`. The new server can be deleted or kept. After the DNS switch, rolling back is the same plus the A record pointed back at the old IP.
