Skills are organized into bucket folders under `skills/`:

- `engineering/` — daily code work
- `productivity/` — daily non-code workflow tools
- `in-progress/` — drafts not yet ready to ship

Every skill in `engineering/` or `productivity/` (the **promoted** buckets) must have a reference in the top-level `README.md` and an entry in `.claude-plugin/plugin.json`'s `skills` array (the Claude Code plugin ships exactly the promoted set). Skills in `in-progress/` must not appear in either.

Installers that scan GitHub for `SKILL.md` files find more than the promoted set: Laravel Boost's `boost:add-skill` matches **every** `SKILL.md` in the repo with no exclusion mechanism — so the README's Boost instructions use the bucket-scoped paths (`witify/skills/skills/engineering`, `witify/skills/skills/productivity`); never document a bare `witify/skills` install. skills.sh also scans `.claude/skills/` but honors `metadata.internal: true` in a skill's frontmatter — every repo-local dev skill under `.claude/skills/` must carry that flag so it stays unpublished.

Most skills are vendored from the upstream [mattpocock/skills](https://github.com/mattpocock/skills) repo, some with deliberate local adaptations. To pull upstream updates, run the repo-local `/upstream-sync` skill ([.claude/skills/upstream-sync/SKILL.md](./.claude/skills/upstream-sync/SKILL.md)); its `STATE.md` records the last-synced upstream commit and the adaptation ledger — never overwrite a ledger-listed file with upstream's copy blindly.

The repo is also its own single-plugin Claude Code marketplace: `.claude-plugin/marketplace.json` lists the one `witify-skills` plugin. `.claude-plugin/plugin.json`'s `version` must always equal `package.json`'s — Claude uses the plugin `version` to decide when installed users see an update; the release flow below syncs it via `scripts/sync-plugin-version.mjs`, so never bump either by hand. Run `claude plugin validate . --strict` after touching either manifest. Why a Claude plugin but not (yet) a Codex one lives in [.agents/adr/0002-ship-as-a-claude-code-plugin.md](./.agents/adr/0002-ship-as-a-claude-code-plugin.md).

`CHANGELOG.md` and version bumps are generated by [changesets](https://github.com/changesets/changesets), never made by hand. Every user-visible change lands with a changeset — a small file in `.changeset/` naming the bump (`major` for breaking changes, `minor` for new or changed skills, `patch` for fixes) plus the prose that becomes its changelog entry, so write that prose for the reader. Releasing is automated by the Release workflow: any changeset pushed to `main` makes it open (or update) a **"chore: version skills" PR** on the `changeset-release/main` branch, accumulating every pending changeset; **merging that PR is the release** — it bumps both manifests, regenerates `CHANGELOG.md`, and CI then tags the version. Never run `changeset version` locally against `main` — it races the PR and leaves it stale.

Each skill entry in the top-level `README.md` must link the skill name to its `SKILL.md`.

Each bucket folder has a `README.md` that lists every skill in the bucket with a one-line description, with the skill name linked to its `SKILL.md`. The promoted buckets' `README.md`s and the top-level `README.md` group entries into **User-invoked** and **Model-invoked**; non-promoted bucket `README.md`s use a flat list.

Skills in `engineering/` and `productivity/` also have a human-facing docs page at `docs/<bucket>/<skill-name>.md` (the docs tree mirrors those two bucket folders under `skills/`). When you add, rename, or change the behaviour of a skill in `engineering/` or `productivity/`, create or re-sync its docs page following [.agents/writing-docs.md](./.agents/writing-docs.md). Skills in the non-promoted bucket (`in-progress/`) get **no** docs page.

Every `SKILL.md` is either user-invoked (`disable-model-invocation: true` plus `policy.allow_implicit_invocation: false` in `agents/openai.yaml`, reachable only by the human) or model-invoked (model- or user-reachable). See [.agents/invocation.md](./.agents/invocation.md).

[`ask-witify`](./skills/engineering/ask-witify/SKILL.md) is the router that maps every user-reachable skill and how they relate. The same trigger that re-syncs a docs page applies to it: whenever you add, rename, remove, or change how a user-reachable skill fits the flows, re-read `ask-witify`'s `SKILL.md` and update it so the map stays accurate — a new skill it never mentions, or a stale one it still routes to, is a router that lies.

To (re)link every skill into the local harness skill directories (`~/.claude/skills`, `~/.agents/skills`), run `scripts/link-skills.sh`. Each entry is a symlink into this repo, so a `git pull` keeps installed skills current; re-run the script after adding, removing, or renaming a skill.
